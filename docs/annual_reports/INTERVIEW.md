# 年报分析助手：面试介绍与追问准备

这份材料以新增年报应用为主线。项目接入 OpenHarness 的原生工具、参数校验、权限和执行结果体系，模型配置与凭据解析复用已有能力；新工作集中在 PDF 证据、复核流程、计算、问答、发送确认和导出。下面的介绍对应已完成的第一版，具体结果见 [验收记录](EVALUATION.md)。没有虚构访谈、用户数或效率提升。

## 两三分钟介绍

我做的是一个年报分析助手，目标用户先定位为金融专业学生和初级研究者。用户上传同一家公司两期中文年报，核对收入、利润和现金流等六类指标，查看同比与原文出处，再导出分析底稿。

我是金融学背景，希望转向 AI 产品经理。这个项目里，我重点考虑的是怎样把模型能力放进一个有明确验收条件的工作流程。

我把流程拆成自动提取、人工确认、程序计算和模型解读。提取数字先作为候选，用户可以打开源页核对或修正。只有明确了年度、单位、币种和合并口径的确认值，才进入计算。

金额转换和同比使用 Decimal，缺失不补零，零或负数基数不报常规增长率。较新年报的上期可比数与旧报告不同时，优先采用较新的同表口径，并提示核对重述或提取差异。

技术上，我把查询、读取原文页和比较封装为三个 OpenHarness 原生只读工具。实际请求经过参数校验、PLAN 权限检查和执行上下文，再返回带来源的标准结果。模型配置复用已有能力，应用通过 `oh reports` 启动。

指标问题优先本地回答；原因和风险类问题先检索证据。可选 DeepSeek 解读先展示准确的发送内容，用户确认后才请求。预览与资料版本绑定，有时效且只能使用一次。这里是受限工具工作流和单次解读，没有开放模型自主执行 Shell；模型也不能覆盖确认值。

验证使用了同一家上市公司的两份真实中文年报，18个金额及来源、6项同比与人工核对的原文一致；另完成了单位、负数、零基数、缺失、公司不匹配、口径和发送确认等边界测试。这些结果只代表当前样本，不是所有年报的通用准确率。

目前还没有规模化用户数据。下一步会观察目标用户完成同一任务的过程，测量复核时间、来源准确性和完整任务完成情况，检验它是否减少了查找和核对工作。

## 八个深入追问

### 1. 为什么不直接把年报上传给一个聊天工具？

直接提问适合灵活探索。这个产品选择固定一条可复核流程：字段有统一口径，数字有年度和单位，出处能逐页回查，确认状态能保留，最终可以导出底稿。它的价值假设是减少重复查找和核对工作。是否比现有方式更省时，要通过同任务对照测试验证，目前不宣称已经证明。

### 2. 为什么先做这六个指标？

它们覆盖业务规模、盈利、经营现金流和期末资产权益，而且常见于年度主要会计数据表。第一版先集中检查少量指标的准确性和可比性，便于建立评测集。选择它们不是因为它们足以判断公司价值；更复杂的行业指标和财务判断需要另行设计。

### 3. 为什么需要人工确认？会不会让产品更麻烦？

会增加一步操作，这是明确的取舍。PDF 表格容易出现列错位、跨行、单位和重述问题，一个错误数字还会被计算和文字解读放大。第一版让用户在源页核对后再计算。后续要测量每项复核的时间，识别哪些场景值得优化。用户点击确认也不等于数字必然正确，因此来源仍然保留。

### 4. 两期报告口径不同怎么办？

先检查公司、年度和币种，再检查指标是否为合并口径以及金额单位是否明确。优先采用较新年报同表披露的上期可比数。与旧报告不同会提示核对，不把旧值悄悄替换进来。母公司报表、单位不清、多候选冲突或无法确定重述列时，暂停计算并让用户处理。

可以举例：旧年报披露上期收入 100，较新年报的可比数是 110，本期是 120。若确认应使用 110，同比分母就是 110；旧披露 100 仍应作为差异提示保留。这是解释规则的示例数值，不是项目的真实公司数据。

### 5. 为什么让程序算数字、模型做解释？

金额单位转换和同比有明确公式，适合确定性程序。模型主要帮助组织和解释已有证据，但不能凭变化直接生成经营原因。系统也不会让模型输出自动覆盖已确认数字。这样可以分别验证提取、计算和解读，错误出现时更容易定位环节。

实现上，计算使用 Decimal，先检查公司、币种、单位和合并口径。模型收到的是固定请求里的已确认事实和少量原文节选，没有被赋予执行程序、修改指标或继续调用工具的能力。引用编号也会与本次提供的来源集合核对，但编号合法仍不能代替语义核查。

### 6. 你怎样处理隐私和外发风险？

默认在本地完成提取、复核、比较和检索。使用 DeepSeek 前，先生成精确发送预览，用户明确确认后才发送对应内容。预览与资料和复核结果版本绑定，有十分钟有效期且只能发送一次；服务只连接官方 HTTPS 地址，不跟随重定向。

外部服务仍会接收获准发送的数据，本地资料也有留存风险，所以不能声称数据全程不出本地或绝不泄漏。只读工具权限与模型外发批准是两个独立检查，第一版也没有完成全面 DLP 或安全审计。

### 7. 怎么评估？你取得了多少提升？

我把评估拆为提取、计算、来源、完整流程和发送边界。提取要与独立人工基准比较；计算覆盖不同单位、负数、零基数和缺失；来源要验证页码与原文；完整流程要能导出带确认状态的底稿；模型请求要验证批准前没有外发、批准后与预览一致。

真实年报评测结果和自动化测试结果分别记录。当前没有用户对照实验，就不报节省时间或效率提升。后续会让目标用户用同一组资料完成同一任务，再比较耗时、错误和纠错成本。

### 8. 你具体接入了哪些 OpenHarness 技术？贡献和难点是什么？

我把原来的通用交互能力收缩到一个明确的金融资料工作流，设计并落地了候选到确认、计算和解读分离、逐页来源与发送预览等环节。

技术上，三个年报工具继承框架的 `BaseTool`，通过 `ToolRegistry` 注册并导出 schema，输入用 Pydantic 校验，再经过 `PermissionChecker` 的 PLAN 只读检查，在 `ToolExecutionContext` 中执行，返回含来源 metadata 的 `ToolResult`。本地问答、原文页和比较结果的实际接口都走这条链。模型配置和密钥解析继续复用已有能力，新增业务代码集中在年报模块。

这不是把完整通用 Agent 循环直接开放给金融文件。当前没有自定义训练，也没有语义向量检索或模型自主调用工具循环。模型解释通过独立的单次请求完成，避免用户批准后的执行范围持续扩大。

难点在于处理可信度与使用负担：自动化能减少操作，但错误需要在进入分析前暴露；确认可以保留用户控制，但确认太多又可能让人机械点击。第一版先保证错误可见、结果可查，接下来再用真实使用过程决定如何减轻复核负担。

## 面试前的演示顺序

1. 打开应用，载入有公开来源的两份中文年报。
2. 展示候选数值，说明它们还没有进入正式计算。
3. 打开一个指标的源页，核对并确认本期和上期值。
4. 展示由程序计算的同比；如需说明缺失或零基数边界，可运行对应测试，不把示例公司的真实数字改成假数。
5. 询问一个指标问题和一个原因问题，解释两条回答路径的差别。
6. 打开模型发送预览，说明批准边界；没有配置或不愿外发时直接取消。
7. 导出底稿，检查数值、状态和来源是否一起保留。

需要展示技术接入时，可以查看应用状态中的 OpenHarness 标识、三个工具名称和 PLAN 模式，再结合 `harness.py` 讲参数与权限如何实际约束执行。原生工具 schema 可以从桥接器读取；当前 DeepSeek 请求不发送工具 schema，不要把它讲成模型正在自主 function calling。

演示只说明相应流程和样本表现，不推导全部年报适配、全局准确率或商业效果。真正能体现产品判断的是讲清楚目标、取舍、证据与尚未验证的部分。
